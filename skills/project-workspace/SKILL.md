# Project Workspace

让项目文件能找到、任务能接续。主要面向同一机器上的持续工作；记录保存在目标项目内，不依赖聊天历史、某个账号或额外服务。

## 确定范围与动作

- 用户指定的目标目录优先；否则沿用当前项目已登记的工作区根，尚无约定时使用当前目录。工作区可以包含多个 Git 工程，不强制等同于 Git 根，也不在每个子目录重复初始化。
- 先读适用的 `AGENTS.md`、项目导航及相关任务入口。既有 `agents.md` 等规则也要检查；不要因为大小写不同而忽略或覆盖内容。
- 按请求选择 **初始化**、**交接**、**恢复**。已经初始化的项目直接处理当前动作；重复初始化只补缺漏、更新已有约定。
- 保留用户已授权的任务范围。初始化本身不包含历史目录搬迁、软件安装、账号配置变更、启动实验或发布。
- 需要新建说明或任务记录时，按需读取 [templates.md](references/templates.md)。模板按项目实际情况裁剪，不生成无内容的条目。

## 初始化

1. 浅层检查现有目录、入口文件和工作记录，包括根层隐藏文件。区分研究工作区与其中的代码工程，列出根层非 `.md` 文件、缺失的目录说明及不符合日期命名的任务/结果入口。
2. 在根 `AGENTS.md` 合并一段简短的工作区约定：各类文件实际位置、如何找到任务、何时保存进度。使用模板的标记块；重复执行更新该块，保留其余内容。已有同义约定则直接维护原段落，避免两份规则。
3. 在根 `README.md` 合并目录导航和任务入口，目录链接优先指向各自的 `README.md`。只列需要导航的目录、任务及重要报告，不递归枚举文件；当前事实以任务记录为准。
4. 新工作区建立 `code/`、`resources/`、`results/`、`scripts/`，各附 `README.md`；更深子目录和 `.agents/tasks/` 按需建立。已有布局先登记实际映射，补齐说明；用户已授权整理时，再按本技能的归属和命名规则迁移，修正引用。
5. 有本机环境需要登记时，按模板建立 `.agents/local.md`。如工作区受 Git 管理，优先在 `.agents/.gitignore` 精确忽略 `/local.md`，复用等效的已有规则；不为此新增根层 `.gitignore`，也不整体忽略任务或决策记录。环境锁文件保留在所属代码工程。
6. 按下述规则核对根层文件、目录说明及其链接，检查重复规则。报告未完成的迁移项，不将其视为符合目录约定。核对新会话能从目标工作区加载根规则；无法验证时明确说明。

若只有小写 `agents.md`，创建标准入口前先核对其内容和引用。优先合并为一份有效规则；兼容入口确有需要时明确指向同一份正文，避免两份独立维护。调整后的规则是否加载需在新会话核对。

## 根层整洁与目录说明

- **工作区最外层只允许目录和 `.md` 文件。** 脚本、配置、锁文件、日志、图片、压缩包、权重等放入所属目录；代码工程自己的配置放在工程内部。隐藏的非 Markdown 文件、指向非 Markdown 文件的根层软链接也需归位，不能用隐藏或改后缀绕过约定。
- 规则针对工作区最外层，不限制内部工程的原生文件结构。工具要求配置固定放在其工程根时，优先将该工程放在 `code/<工程>/`；不盲目移动配置导致工具失效。
- 已有根层非 Markdown 文件先核对用途、引用和运行依赖，再按用户授权迁移并修正入口。尚不能迁移的项目明确列为待处理，保留原件，不自动删除。
- **每个一级业务目录都必须有 `README.md`**，包括 `code/`、`resources/`、`results/`、`scripts/` 以及实际使用的其他业务目录；工作区管理目录 `.agents/` 存在时也提供简短导航。沿用并更新已有 README，不另建同义说明。不向 `.git/` 等工具内部目录批量添加文件。
- 目录 README 说明用途、收纳边界、实际的一至两层结构及主要入口，并使用相对链接。空的基础目录写明用途和“暂无内容”，不虚构工程或产物。
- `code/README.md` 索引工程与用途；`resources/README.md` 索引论文、软件及必要的来源和版本；`results/README.md` 索引任务结果、报告和复现入口；`scripts/README.md` 说明通用工具的用途、调用方式、依赖及输入输出。详细内容保留在所属工程或任务中，导航不复制正文或运行状态。
- 新增、迁移、重命名主要目录或产物入口时同步更新最近一级目录 README；改变一级布局时同步更新根 README。有独立用途的深层目录按需补说明，不给每层缓存、权重或第三方源码目录机械生成 README。

## 文件归属

按内容在项目中的用途归类，具体路径服从已登记的映射：

| 内容 | 默认位置与约定 |
| --- | --- |
| 持续维护、修改的代码 | `code/<工程>/`；工程内部保持其原生结构 |
| 下载的论文、标准、原版编码器 | `resources/`；保留来源和版本身份 |
| 分析、报告、图表、实验与交付产物 | `results/YYYY-MM-DD-topic/`，或分类下的同格式目录；不同运行各自按日期命名 |
| 可供相似任务复用的脚本、辅助代码 | 顶层 `scripts/`；保留单一实现，输入输出通过参数指定 |
| 一次分析专用的复现脚本 | 对应日期结果目录；确认有复用用途后提取到 `scripts/`，所属工程的专用代码仍在工程内 |
| 当前讨论、假设、进展和下一步 | 当前任务记录 |
| 长期决策、理由及验证边界 | 沿用 `.agents/notes/` 或项目已有决策目录 |
| 临时中间文件 | 当前任务或结果目录内的临时子目录；不散放根目录 |

- 固定版本的软件记录来源、tag/commit 或归档校验值。需要修改时使用工作工程，保留与原版的关系；代码版本由 Git 等实际版本机制标识，不靠 `final2` 等名字。
- 大数据、权重和外部存储记录稳定路径及身份，避免为每个任务复制。一次运行的配置、日志、结果与代码版本应能互相追溯；有未提交修改时，仅记录 commit 不足以复现，应保留差异及相关新增源码或适当快照。
- 不确定用途的外来材料可临时放 `resources/inbox/`，首次使用时归位；不把它变成永久杂物目录。
- `scripts/` 可放日志汇总、结果比较、格式转换等通用工具；脚本生成的报告和临时产物写入对应任务的结果目录，不能把 `scripts/` 当成另一处输出目录。不要仅为建立目录而编写尚无用途的工具。

## 任务与结果目录命名

- **任务目录统一为 `.agents/tasks/YYYY-MM-DD-topic/`**，例如 `.agents/tasks/2026-09-29-decoderunify/`。日期必须是实际有效的日历日期；不使用 `20260929-topic` 或仅在末尾追加日期。
- **承载一次任务、实验或独立运行的结果目录同样以 `YYYY-MM-DD-` 开头**。允许中间的用途分类，如 `results/experiments/`、`results/training_runs/`、`results/analysis/`；分类下真正保存一次结果的目录需要日期前缀。若任务内另建独立运行目录，该运行目录也按其启动日期命名。
- 例如 `results/experiments/hdrf477k_align16_resume100_from_epoch0299_20260916/` 应整理为 `results/experiments/2026-09-16-hdrf477k_align16_resume100_from_epoch0299/`；不保留一层无日期的同名运行目录来包裹实际产物。
- 日期用于任务/结果身份，不要求给内部功能目录 `checkpoint/`、`logs/`、`figures/`、`source/`、`code_snapshot/` 等加日期，也不改写冻结归档的内部结构。
- 新任务使用创建日期，新运行使用启动日期；恢复同一任务或运行时沿用原日期。整理历史内容时优先采用用户指定日期或有记录支持的原日期，包括可信的原目录日期后缀。无法核实时使用本次登记日期，并在对应记录中注明“登记日期；原始日期未核实”，不冒充历史发生时间。
- 主题名简短且可识别；同日重名时加有意义的区分或序号，不覆盖已有目录。不同任务各自命名；同一任务与它的不同运行可有不同日期，用链接关联。
- 已授权整理时直接迁移原任务/结果目录，复用原记录，不建立第二份状态。同步更新导航、当前路径引用和必要配置，保留旧名到新名的对应；历史实验 ID、原始来源和测量结果不因目录改名而篡改。受运行依赖或冻结归档约束暂不能迁移时，明确列为待处理，不宣称命名检查通过。

## 任务入口与交接

一个持续任务对应一个稳定的 `task-id`，格式为 `YYYY-MM-DD-topic`，例如 `2026-11-13-codec-compare`。同一任务跨会话沿用 ID；无关任务各自记录，避免共享一份不断覆盖的“当前任务”。

新任务默认使用 `.agents/tasks/<task-id>/state.md`。已有规划三件套或其他有效记录时，指定现有文件作为恢复入口，在项目导航登记它，补足恢复信息；已授权的目录改名按上节执行，不额外维护内容重复的 `state.md`。

交接时直接更新当前任务入口：

- 保存目标、用户约束、讨论结论及理由、未解决问题、已尝试但不成立的方向。
- 写清已完成与未完成事项；关键判断链接到报告、代码、配置或日志。区分计划、观察、推测和已验证结论。
- 记录工作目录、代码身份、环境引用、输出位置、运行作业标识及最近检查时间；聊天会话 ID 仅在已知时记录，不猜测、不默认扫描全机聊天存储。
- 下一步写成具体动作。内容以足够接手为准；长篇调查按需拆到任务目录并从入口链接，避免复制整段聊天或原始日志。
- 长期决策使用已安装的 `project-notes` 或项目现有约定；只在有长期价值时记录，任务文件保留链接。没有该技能时不为交接自动安装它。

在重要讨论结论形成、完成阶段、遇到阻碍、准备切换账号或结束工作时更新。长任务启动前先保存命令、配置和输出位置，启动后补作业标识；突然中断只能恢复到最近落盘点。

调用规划、访谈等其他技能时，先把当前任务目录和唯一恢复入口传给它们。新记录遵循项目路径约定，已有记录可从入口链接；不因使用另一个技能另建一套竞争的任务状态，也不自动修改用户的全局技能。

## 恢复

1. 从用户指定的任务或项目导航定位入口。任务唯一时直接使用；多项都可能匹配时用一条简短问题确认，不按文件修改时间猜选，也不恢复所有任务。
2. 读取入口、相关证据和必要的本机环境条目，确认目标、代码位置、当前状态及下一步。
3. 核对与下一步相关的实际文件、版本、环境和作业。作业标识结合主机、命令、启动时间或日志验证，不能仅凭旧 PID 或“运行中”文字重启或停止任务。
4. 沿用用户已有授权继续下一步，并更新记录；若只是要求查看恢复情况，则给出状态。恢复失败说明具体缺失项，保留已经找到的证据。

聊天恢复和进程恢复都是辅助入口：

- Codex CLI 可用 `codex resume <SESSION_ID>`；`--last` 受当前目录筛选，`--all` 放宽目录筛选。使用前按实际安装版本核对帮助，不把 `--all` 当成跨账号历史同步。
- 切换账号工具若改变 `CODEX_HOME` 或历史存储，原聊天未必可见；新会话仍可从任务文件继续。其他 Agent 同样使用这些文件。
- 同机终端可用 `tmux new-session -A -s <项目会话名> -c <绝对工作区路径>` 保留入口；记录实际名称。训练使用独立会话和持久日志。tmux 不恢复已退出进程或 VSCode 扩展聊天界面。
- 不自动改账号、复制凭据或把会话恢复命令当作任务完成。凭据不进入状态文件。

## 完成检查

扫描根目录直接条目（包括隐藏项和文件软链接），确认没有未归位的非 `.md` 文件；逐一检查含 `scripts/` 在内的一级业务目录及已有 `.agents/` 的 README、结构描述和相对链接。检查任务目录和实际结果/运行目录是否以有效的 `YYYY-MM-DD-` 开头，避免误查分类或内部功能目录。再确认通用脚本已归位、任务入口唯一且可找到、下一步明确、运行状态带检查时间。存在遗留违规项时列明，不能报告整洁或命名检查通过。回复给出相关入口与实际检查结果即可。

本技能不安装 hooks，不承诺每轮自动保存；初始化写入的根规则用于后续会话。换机器时还需要同步项目与环境，不能只依赖本机路径。
